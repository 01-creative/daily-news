【高危·EDUSRC·二进制】CVE-2026-80521 — Linux 内核 AF_UNIX 释放后使用，容器内可直达宿主 root，且**公开 EXP 已发布**

这是本窗口最该先看的一条。**9/23–9/24** 期间，DepthFirst 公开了针对 **Ubuntu 26.04 LTS** 实测通过的利用代码（并已在 GitHub 放出 PoC）。根因在内核 AF_UNIX 套接字的垃圾回收：通过 `SCM_RIGHTS` 传递文件描述符时存在竞态，回收器可能在新引用入队前就看到它，从而在一组链式套接字中释放掉一部分却**没有从持久化内部列表里摘掉指针**，下一轮回收顺着悬垂指针走进已释放内存（`unix_vertex` 被释放后遗留的 `scc_entry` 链指针）。缺陷代码引入于内核 6.10 并回移植到 6.1/6.6 稳定分支。

**为什么严重**：AF_UNIX 套接字在 Docker 与 Kubernetes 的默认 seccomp 配置里是放行的，因此**普通系统调用即可触达**，绕过命名空间隔离、cgroup 限制与 seccomp 过滤，直接拿到宿主 root。上游补丁在 **8 月 6 日**（主线 7.2、稳定 7.1.10）就已合入，但**Ubuntu 至今未向任何受影响版本发布修复**——26.04 LTS 在 Ubuntu tracker 上仍标 "vulnerable, work in progress"，24.04 LTS 及 22.04 的部分 HWE/AWS/Azure/GCP 云内核同样在列。目前无在野利用证据、未入 KEV。

**对高校**：实验室与实训平台的 Docker/K8s、跑学生提交代码的评测机（OJ、CI runner）、多租户共享的计算池，都属于"容器边界即安全边界"的典型误用场景。DepthFirst 的结论很直白：**容器不应再被当作安全边界**——2026 年已发布近 5,700 条 Linux 内核 CVE，"攻破容器边界攻击内核的门槛已大幅下降"。无法立即打补丁时，官方建议把不可信负载迁到 microVM 隔离（Firecracker 或 Kata Containers），让每个负载跑自己的内核。

（9/23–9/24 公告批次。本批共同点依旧是"智能体的安全属性不由模型单独决定"——三条分别打在推理链、激活态与路由标识上。）

Control-Token Injection：一行控制符即可**关停思维链**，并让基于推理的监督全线失效（arXiv:2609.27542，9/23 提交，cs.CR）

作者提出的判断很锋利：工具调用型智能体的安全性**不是模型自身的属性，而是"模型 + 周边软件"（chat template 渲染器、工具调用解析器、解码框架）的共同属性**，而两侧都能被不可信输入攻击。

具体到实验：在已发布的 **gpt-oss-20b** 推理模型及其官方工具沙箱上，只要在用户消息末尾**附上该模型自己的通道控制 token**，tokenizer 就会把这一轮推理渲染成"已经结束"，模型**不再产出任何思维链，直接跳到工具调用**。在模型本已能处理的 40 多个任务上，推理通道**从平均 52.5 token 直接归零，且每一次试验都为零**，而工具调用照常触发。后果是监督层的整体失守：一个规则监视器与一个跨家族 LLM 监视器**在所有正常试验上都标记了该不安全请求，在所有伪造试验上一条都没标记**；对于明确恶意的请求，该攻击把模型 **39.6% 的拒绝转化为已完成的窃密**。

另一组发现同样值得警惕：一个等价的工具调用是否真的触发，**取决于 harness 的解析器而非模型**——容忍截断的正则会在缺少闭合 token 时照样触发，严格的正则则直接丢弃；某智能体随附的两个解析器在**完全相同的贪心生成**上给出相反结果（24 次全触发 vs 一次都不触发）。该抑制也可**间接投递**。作者评估了输入清洗、解析器加固与"空推理检测"三类防御：标记缺失的推理轨迹能挡住基础攻击，但面对**自适应的良性诱饵**即失效。全部测量基于公开模型的贪心解码，代码与逐次试验日志均已公开。

→ https://arxiv.org/abs/2609.27542

Your Model Is Leaking：残余流里的隐蔽信道，让"气隙 + 只导出诊断产物"的假设失效（arXiv:2609.27996，9/23 提交，cs.CR）

针对的是一类常见合规架构：模型跑在受限或气隙环境里，只允许**导出部分诊断产物**。本文的结论是——被攻陷的运行时组件可以把敏感数据**藏进被允许外传的中间激活值**里，而**离线观察者用一个简单的线性解码器就能还原**。攻击不需要重训模型、不改权重、不掌控出网通道，也无需控制记录器或传输机制，只需一个被污染的运行时钩子把消息映射为码字、注入某一中间残余流，注入强度按局部残余范数缩放（作者称"信噪比-残余范数比"）以保持可恢复性。

跨 **7 个架构家族共 11 个模型**评测：**9 个模型恢复率 91%–100%**，KL 散度仅 0.001–0.007，而**激活层检测器的表现接近随机（AUC ≤ 0.56）**，测试过的后验防御**均无法可靠消除该信道**。作者的落点很干净：一份激活产物**可以同时是 schema 合法的、又携带了不该越界的信息**。凡在做模型产物脱敏、跨域导出审计与"可信执行环境 + 诊断回传"设计的团队，这条直接冲击其信任假设。

→ https://arxiv.org/abs/2609.27996

Agent Name Collision Attacks：A2A 把名字当元数据，实现却把它当身份（arXiv:2609.27624，9/23 提交，cs.CR）

多智能体宿主会把远端 Agent Card 转换成本地智能体、工具、工作流目标与经纪人路由。问题在于 **A2A 协议把 card 的 name 定义为"人类可读的元数据，而非稳定身份"，也没有规定冲突处理**——可当宿主把这个远端名字直接**当作本地路由标识**使用时，碰撞就出现了。作者沿注册→派发全链路追踪，并在 **7 个固定版本的开源实现**上做了隔离回归测试：**6 个客户端式集成**中，一个本应发给可信对端 A 的请求被导向了**攻击者控制的对端 B** 的客户端或回环端点；第 7 个经纪式实现把两个对端**合并到同一条由名字派生的路由**上，此时"队列与访问控制状态决定结果是拦截还是拒绝"。作者强调典型后果是**发错对端，而非普遍性的权限继承**——合成凭据与工具测试中未观察到 A 的凭据或 A 专属工具被直接转移，经纪路径会透传调用方配置对象，因此被委派的身份或令牌只有在"确实存在且 B 能用该路由"时才会到达 B。

作者把必要条件摊到协议、实现与部署三方：宿主应**按来源绑定的稳定标识路由、让名字只承担展示作用、拒绝歧义别名**。这是"一类反复出现的实现层漏洞"，而非某个通用协议利用。正在接入 A2A 或自建智能体网关的团队可当清单对照。

→ https://arxiv.org/abs/2609.27624
